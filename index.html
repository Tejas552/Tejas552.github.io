Reading paperwork automatically

Turning scanned factory paperwork into searchable data

Live in production
The problem

Batch manufacturing records are filled in by hand on the floor, scanned, and archived as images. Finding a specific process value later meant a person opening PDFs and reading them — including tables with handwritten entries. There was no way to search or aggregate any of it.

What I built

A Streamlit application on top of Azure Document Intelligence that reads scanned batch records, including handwritten table entries, and extracts them straight into structured Excel output. It's used two ways day to day: pulling specific process values out of archived records for retrospective analysis, and bulk table extraction for the QA team, who previously hunted for a separate tool to do that job.

Where it stands

Deployed on Streamlit Community Cloud with credential handling for internal use; an Azure-internal deployment behind the company VPN is planned next, wired into the same GitHub deployment flow the rest of the team already uses.

Checking quality from a photo

Turning a microscope photo into data anyone can search

Live in production
The problem

An operator looks down a microscope, and what they see — cell count, and how many of those cells are carrying inclusion bodies — is a real signal for how a batch is performing. That signal was going unrecorded, or recorded without any link back to the process parameters that might explain it.

What I built

A tool that takes an operator-captured microscope image, counts cells and inclusion-body-positive cells, and joins that result back to the process parameters for that batch — turning a visual check into a queryable dataset the process team can look at alongside everything else they track.

Rebuilding it properly

I later rebuilt this project as a personal learning exercise, following good software practices: moved every setting into one config file, split one long script into clear parts (reading images, extracting data, applying rules, writing reports), and wrote 28 automated tests. The factory computer has no internet access, so those tests use Python's built-in testing tool rather than one that needs downloading. Every accept/reject decision is now saved in a clear log instead of just printed and lost.

An AI helper that stays on-site

An AI assistant for finding root causes — that never leaves the building

In progress
The problem

When something goes wrong on the floor, figuring out why often means remembering how a similar problem was solved months or years ago — and that memory lives in a few people's heads, not anywhere searchable. Any tool built to help has one hard rule from the start: this data cannot leave the building, which rules out every cloud-based AI service.

What I'm building

An AI assistant that reads through past investigation records and suggests likely causes for a new problem — built to run entirely on a local computer, using a free open-source language model. Nothing about the investigation ever gets sent over the internet.

Where it stands

In progress: it can already search past records and suggest causes. Next, I'm checking how good those suggestions are against cases where the real cause is already known.

Machine learning · Process yield

Using machine learning to close the gap between average and best-case yield

In progress
The problem

For a small-molecule API, the best possible yield the chemistry allows is 56%. Real batches were averaging 51% — a real, persistent gap, with no clear answer for which of the hundreds of process steps and settings were actually responsible.

What I built

Working with process experts, I started from 313 possible features across every stage of the process — timings, temperatures, pH, quality-check results — and narrowed that down to 217 that actually mattered. I used correlation analysis built to catch non-linear relationships (a chemical process rarely responds in a straight line) to find which steps were quietly dragging yield down, including one heating step and one temperature limit that both needed tightening. I then tried a wide range of models to find the best fit, and used an optimization algorithm to solve for the exact settings that would push yield higher.

Judgement calls worth naming

Some settings looked statistically important but weren't things anyone could actually act on — known only after a test result came back, or already fixed earlier in the process — so I left them out of the recommendations, even though including them would have made the model look better on paper. One recommended amount also got rounded to match the real pack size the raw material is delivered in, since the mathematically "perfect" number wasn't something the floor could actually measure out.

Where it stands

Recommendations are with the process team; some of the biggest remaining drivers (heating and cooling times) turn out to depend on the weather outside, which nobody can control — so the honest ceiling on this project is lower than the model alone would suggest.

Applied LLMs · Quality & operations

A chatbot that answers questions across quality, engineering and process data

Live in production
The problem

Answering one question — about a deviation, an engineering issue, or a process trend — usually meant checking SAP, an Excel tracker, and an Azure system separately, then piecing the answer together by hand.

What I built

Two connected pieces. First, a custom chatbot, built with ChatGPT's custom chatbot feature, fed with quality, deviation, engineering and process data pulled from SAP, Excel and Azure, so people can ask a plain-language question and get an answer without opening any of the source systems. Second, a LangChain-based tool that connects straight to the same data in Azure Data Lake using SQL underneath, so questions can be answered against live data instead of a periodically refreshed copy.

Where it stands

In use for day-to-day questions across quality and engineering, with the direct data-lake connection covering the cases where the answer needs to reflect what's true right now.

How I work

Four habits I've learned from working in a regulated factory.

Work with what's there

Build for the computer you actually have, not the one you wish you had

The factory computer has no internet access, so tests run on Python's built-in unittest tool instead of one that needs downloading. Quality data can't leave the building, so the AI helper runs entirely offline on a local model. What's actually available decides how something gets built.

Catch it early

Catching a mistake early is cheap. Finding it later is expensive

Missing data entries used to surface a month later, if at all, and quietly threw off every average calculated from them. Flagging the gap within days, right at the source, mattered more than anything clever done with the numbers afterward.

Build vs. buy

Building it ourselves was cheaper than buying it

There was a paid tool that could read scanned records. Building the same thing in-house cost less, and it meant we owned the tool for whatever came next.

Do it properly

A script that works once isn't the same as one that lasts

The microscope-photo tool worked fine before it had settings, tests, or clear sections. I gave it all three anyway — because a tool only one person can safely change becomes a problem the moment that person is unavailable.
